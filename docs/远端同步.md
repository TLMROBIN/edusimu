# 远端同步

这份文档面向：

- 后续继续在本机开发的人
- 需要把本机改动同步到局域网新服务器的人
- 接手本项目的 AI / 运维人员

它解决的问题不是“怎么首次迁移”，而是：

- 以后代码应该在哪里改
- 改完后如何稳定同步到远端
- 为什么不能直接去远端手工改代码

---

## 1. 当前约定

当前推荐维护方式是：

- 只在本机源码目录里改代码
- 不直接在远端服务器手工改业务代码
- 每次改完后，通过一个固定脚本把代码同步并发布到远端

当前本机源码目录：

- `/home/binyu/文档/trae_projects/edusimu`

当前远端服务器：

- IP：`10.50.159.62`
- SSH 用户：`yub`
- 对外访问地址：`http://10.50.159.62:3003`

当前远端工作区目录：

- `/home/yub/文档/trae_projects/edusimu`

当前远端运行目录：

- 后端：`/var/www/edusimu/backend`
- 前端：`/var/www/edusimu/frontend/dist`

---

## 2. 为什么要这样做

这样做的原因很直接：

- 本机已经具备完整开发环境
- 远端服务器主要负责运行，不适合当主要开发机
- 当前远端前端发布采用“本机构建、远端只同步 dist”的方式，更稳定
- 如果多人或 AI 直接改远端运行目录，线上代码和仓库源码会很快漂移

结论：

- 远端是运行环境，不是主开发环境
- 源码真相以本机工作区为准

---

## 3. 当前同步链路

当前远端同步依赖这几个脚本：

- 本机入口：`scripts/sync_remote_server.sh`
- 远端受限发布入口：`scripts/remote_deploy_bundle.sh`
- 远端后端发布：`scripts/deploy_live_backend.sh`
- 远端前端发布：`scripts/deploy_live_frontend.sh --skip-build`

执行关系：

1. 在本机构建前端 `dist`
2. 用 `rsync` 把源码同步到远端工作区
3. 远端通过受限 `sudo` 执行 `remote_deploy_bundle.sh`
4. 远端发布后端代码
5. 远端发布前端 `dist`
6. 远端检查 `postgresql`、`edusimu-backend`、`nginx`

## 4. 日常同步命令

在本机项目根目录执行：

```bash
cd /home/binyu/文档/trae_projects/edusimu
./scripts/sync_remote_server.sh
```

这是当前唯一推荐的“本机改动同步远端”方式。

执行完成后，访问：

```text
http://10.50.159.62:3003
```

如果页面像没更新，先强制刷新浏览器：

- `Ctrl + F5`

## 5. 这个脚本实际做了什么

### 5.1 本机构建前端

脚本会在本机执行：

```bash
cd frontend
npm run build
```

说明：

- 当前前端是 `Vite 5`
- 远端服务器不作为主要前端构建机
- 前端必须优先在本机构建，再同步 `dist`

### 5.2 同步源码到远端工作区

脚本会把本机项目同步到：

- `/home/yub/文档/trae_projects/edusimu`

同步时会排除这些内容：

- `.git`
- `backend/venv`
- `backend/uploads`
- `frontend/node_modules`
- `tmp`
- `__pycache__`
- `*.pyc`

这意味着：

- 数据库不会被同步覆盖
- 课件文件 `uploads/` 不会被同步覆盖
- 远端虚拟环境不会被整个替换

### 5.3 远端发布

远端会执行：

- `scripts/remote_deploy_bundle.sh`

这个脚本会继续调用：

- `scripts/deploy_live_backend.sh`
- `scripts/deploy_live_frontend.sh --skip-build`

后端发布动作包括：

- 备份远端旧 `app`
- 同步新的 `app`
- 同步新的 `requirements.txt`
- 在远端虚拟环境执行 `pip install -r requirements.txt`
- 执行 `compileall`
- 执行 `init_database`
- 重启 `edusimu-backend`

前端发布动作包括：

- 不在远端重新构建
- 直接把本机构建好的 `frontend/dist` 同步到远端运行目录

## 6. 当前已经配置好的免密能力

### 6.1 本机 SSH key

当前本机已经存在专用 key：

- 私钥：`/home/binyu/.ssh/id_edusimu_sync`
- 公钥：`/home/binyu/.ssh/id_edusimu_sync.pub`

当前本机 SSH config 已配置：

- `/home/binyu/.ssh/config`

作用：

- 本机连接 `10.50.159.62` 时优先使用这把 key
- `ssh` 和 `rsync` 不再要求输入远端登录密码

### 6.2 远端受限 sudo

当前远端已配置 sudoers：

- `/etc/sudoers.d/edusimu-deploy`

它只放行这一条命令免密执行：

- `/bin/bash /home/yub/文档/trae_projects/edusimu/scripts/remote_deploy_bundle.sh`

这意味着：

- 不是“所有 sudo 都免密”
- 只有这个固定部署入口免密
- 比直接给整机 sudo 免密更安全

## 7. 维护者必须知道的限制

### 7.1 不要直接在远端改业务代码

不要把下面这些目录当成主开发目录：

- `/home/yub/文档/trae_projects/edusimu`
- `/var/www/edusimu/backend`
- `/var/www/edusimu/frontend/dist`

原因：

- 直接在远端改，仓库和运行目录会漂移
- 以后本机再次同步时，远端临时改动会被覆盖

### 7.2 不要把同步流程当成“数据迁移”

`sync_remote_server.sh` 只同步代码和构建产物，不同步：

- PostgreSQL 数据库
- `backend/uploads`

所以它是“发布流程”，不是“整机迁移流程”。

### 7.3 前端构建以本机为准

当前远端前端发布走 `--skip-build`，原因是：

- 本机开发环境更完整
- 远端主要承担运行职责
- 即使远端 Node 版本变化，本地构建再同步仍然最稳

### 7.4 依赖变更要提交到仓库

如果后端新增 Python 依赖，必须更新：

- `backend/requirements.txt`

否则远端下次发布时不会自动安装新依赖。

额外注意：

- 当前认证链路依赖 `passlib[bcrypt]==1.7.4`
- `bcrypt` 必须固定为 `4.0.1`
- 不要随手升级到 `5.x`

原因：

- `passlib 1.7.4` 与 `bcrypt 5.x` 组合时，旧账号登录会在验密阶段报错
- 现象通常是 `POST /api/auth/login` 返回 `500`
- 远端日志会出现 `ValueError: password cannot be longer than 72 bytes`

## 8. 新维护者换机器后要做什么

如果后续不是在当前这台本机维护，而是换了一台新的开发机，需要重新配置两件事：

### 8.1 配置新的 SSH key

在新的本机上生成 key，例如：

```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_edusimu_sync -N ''
```

再把公钥装到远端：

```bash
ssh-copy-id -i ~/.ssh/id_edusimu_sync.pub yub@10.50.159.62
```

### 8.2 配置本机 SSH config

例如：

```text
Host 10.50.159.62
  User yub
  IdentityFile ~/.ssh/id_edusimu_sync
  IdentitiesOnly yes
  StrictHostKeyChecking accept-new
```

说明：

- 远端 sudoers 当前是按远端脚本路径放行的
- 所以只要远端工作区路径不变，新维护者不需要改 sudoers

## 9. 常见排查

### 9.1 运行同步脚本时报 SSH 错误

优先检查：

- 本机 `~/.ssh/config`
- 本机私钥是否存在
- 远端 `authorized_keys` 是否包含对应公钥
- 远端 IP 是否仍然是 `10.50.159.62`

### 9.2 同步时又要求输入 sudo 密码

优先检查：

- 远端 `/etc/sudoers.d/edusimu-deploy` 是否还在
- 远端工作区路径是否仍是 `/home/yub/文档/trae_projects/edusimu`
- `scripts/sync_remote_server.sh` 是否仍调用绝对路径的 `remote_deploy_bundle.sh`

### 9.3 同步成功但页面没变化

优先检查：

1. 浏览器缓存
2. 远端 `frontend/dist` 是否真的更新
3. Nginx 是否仍指向 `/var/www/edusimu/frontend/dist`

### 9.4 后端发布失败

优先检查：

- `backend/requirements.txt` 是否缺依赖
- `backend/requirements.txt` 里的 `bcrypt` 是否仍是 `4.0.1`
- 远端日志：

```bash
ssh 10.50.159.62 "sudo journalctl -u edusimu-backend -n 100 --no-pager"
```

### 9.5 服务状态检查

```bash
ssh 10.50.159.62 "sudo systemctl status edusimu-backend --no-pager"
ssh 10.50.159.62 "sudo systemctl status nginx --no-pager"
ssh 10.50.159.62 "sudo systemctl status postgresql --no-pager"
```

## 10. 给 AI 维护者的明确要求

如果你是接手这个仓库的 AI，请遵守下面几条：

- 默认在本机工作区改代码，不要直接编辑远端运行目录
- 如果目标是把本机改动上线到新服务器，优先使用 `./scripts/sync_remote_server.sh`
- 不要把远端同步脚本用于数据库迁移或 `uploads/` 同步
- 如果远端发布失败，优先查 `journalctl -u edusimu-backend`
- 如果你修改了远端工作区路径、远端用户或服务器地址，必须同步更新：
  - `scripts/sync_remote_server.sh`
  - 远端 sudoers 规则
  - 本机 SSH config

---

## 11. 当前结论

当前这套远端同步方案已经具备以下特征：

- 本机开发
- 远端运行
- SSH 免密
- 远端部署入口受限免密 sudo
- 前端本机构建、远端只发布产物
- 后端依赖和代码同步发布

对于后续维护者来说，最重要的一句话就是：

- 改代码在本机，发布用 `./scripts/sync_remote_server.sh`
